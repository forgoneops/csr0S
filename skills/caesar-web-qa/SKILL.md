# Web QA (evidence before "done")

## When to Use
Use for rendered QA of built or served web apps, including local CAESAR consumer previews. For client one-page sites or VPS hosting, use `caesar-client-preview`.

Related: [[caesar-premium-gate]], [[caesar-ui-review]], [[caesar-web-build]].

1. `node ~/.local/share/caesar-skills/hallmark/scripts/sloplint.mjs --render <site>`; fix every Floor finding, do not argue with the linter.
2. For live-feature verification or post-live release QA, compare exact relevant live JS/CSS assets with the candidate and probe the feature API through the authenticated browser (status/content headers plus a harmless existing fixture); do not infer live state from source or `dist` alone. Before restarting, inspect `git status --short`, the targeted diff, process/unit owner, active agent runs, and whether the running server already serves the candidate assets. Do not restart merely because a build completed: if the server reads built assets dynamically, prove the exact live asset matches and verify the feature route instead. Never restart a shared process from a dirty checkout if that would activate unrelated changes or interrupt an active run; isolate the candidate or wait for a safe window. Do not ask repeatedly for routine local/read-only QA or already-authorized reversible steps; evaluate conditional approval first and proceed by the least-disruptive safe route. Ask once only when a consequential action remains necessary and is not covered by authorization.
3. After the final source edit, rebuild the exact candidate and verify its generated assets reflect that source; live and `dist` matching each other can still mean both are stale. Capture the requested mobile widths (if 390/320 are named, capture both), plus 428/1440 as useful baselines; cover Day/Night, every Colour, and Motion off/full. Read back `innerWidth`, document/body `scrollWidth`, hero/art/copy bounds, and overlap. For fixed docks/launchers, measure the exact rectangle intersection with visible actionable controls at the initial scroll position and after relevant scrolling; zero document overflow does not rule out occlusion. After React click actions, wait for the rerender before reading `aria-expanded` or result counts, because same-turn reads can capture pre-click state. Measure every touch target, including text inputs and form actions (44×44 minimum). A global `!important` coarse-pointer rule can override component CSS, so rendered computed/rect geometry, not a source declaration, is the evidence. When one Settings section has undersized touch controls, add a `44px !important` exception scoped to that panel's stable section id inside the coarse-pointer media rule; cover every interactive button variant in its shared subtree, including custom picker triggers and disabled siblings, then verify phone computed sizes and that fine-pointer desktop remains unchanged. For rules gated by `(pointer: coarse)`, enable touch emulation explicitly and verify `matchMedia('(pointer: coarse)').matches`; mobile viewport emulation alone may leave a fine pointer. Wait for CSS transitions to settle before judging computed colours or screenshots; a read during a transition can show the previous palette. If the terminal wrapper rejects a finite `vite build` as long-lived, run the repo-local `./node_modules/.bin/vite build web` with `background=true`, wait for completion, and accept only exit 0 plus successful build output; never substitute a dev server for the build. Remember that `--outDir /tmp` relocates emitted assets only: Vite may still write its bundled-config cache under `node_modules/.vite-temp`. Treat that cache write as a separate approval/write boundary; if it fails or is refused, report the build blocker instead of assuming the temp output path made the whole command isolated or retrying it through another wrapper.
4. `tools/ui-sweep.mjs` for overflow and clipped text across routes (limit 3 heavy browsers; the PC has 7.8 GB RAM).
5. Worst case: long names, empty, many items, no JS, no network for fonts.
6. Lighthouse (performance, accessibility, best practices) on throttled mobile; keyboard-only pass; reduced-motion pass.
7. Claims check: every number, name, logo and quote on the page has a source or is a visible placeholder.
8. Report with the screenshots, before and after, and what you did not check. Statuses: prepared, generated, checked, approved, published; only the operator approves and publishes.

## State-safe browser review

For a local consumer-edition app preview, follow [references/consumer-edition-preview.md](references/consumer-edition-preview.md); this is an isolated app build, not a client-site preview or release.

- For authenticated feature checks, use same-origin `fetch(..., { cache: "no-store" })` and return only status/headers plus stable bundle markers; do not inspect transcript bodies or insert synthetic messages into the operator's history. When a route renders private values (such as locations, forecasts, or message content), assert only booleans/counts/geometry in the browser, never print raw values, and capture only privacy-safe screenshots; if a screenshot would expose those values, omit it and state that visual capture was intentionally limited. If the app shell fails to mount, report API/bundle evidence separately from rendered-UI QA and mark the visual pass partial.
- For interactive tests of autosaving UI, block non-read requests by default; if the interaction needs a settings response, intercept the exact write endpoint in memory, record its payload, return a synthetic merged response, then GET the real state and confirm it stayed unchanged. Restore the real fetch path and reload the UI after the mock. If the live API is older than the candidate, inspect its current contract; use a legacy value only when that API accepts it, normalize it to the canonical user-facing choice in the UI, and keep the canonical migration covered for the next safe restart. Never issue a real PUT just to prove compatibility or save and restore the operator's preferences; never remove the write guard to make interactions work.
- For virtual-keyboard regressions, at each target phone width focus a chat input, emulate a reduced `visualViewport.height`, and assert the frame/composer fit plus keyboard-specific header state. Restore viewport height **without blurring first** and assert the keyboard class clears and header returns while focus remains; then blur and assert again. Blur-first can mask stale focus-derived layout state. Use synthetic data and block chat sends/writes.
- Before dismissing onboarding, tours, or update prompts, inspect the control path for persistence. Capture the relevant preference before the test and block writes; if you cannot establish or guard the prior state, leave the prompt open and report the visual review as partial rather than clicking through and assuming nothing changed. For boot/fallback overlays, wait for the app root and real content to mount, then inspect the HTML fallback's trigger and dismissal logic; a one-shot timer can reveal a warning during slow SPA startup and never hide it after mount. For CAESAR, inspect `web/index.html`. Treat the `.boot` dialog (“HUNTING CORE” / “touch to enter”) as a startup splash, not proof of a login wall: click `.boot-mark` or the splash/page centre, wait about two seconds for the app root `.booted`, then inspect the actual route and auth state. If the page was loaded before entry, reload and repeat; a login screen appearing after boot is a separate auth boundary. If content is mounted but the HTML fallback remains, do not clear caches or click recovery controls just to dismiss it; open a fresh tab, wait for a clean startup, and verify the fallback is hidden, the root has children, and the target route renders before calling visual QA clean. If the fresh tab still fails, report API/bundle evidence separately and mark rendered QA partial.
- For route audits, enumerate the actual live routes first and build a route × tab/state × viewport × theme × language matrix. Capture the requested combinations at the named dimensions; a Home or Settings screenshot proves only that surface, not every route or tab. Record the selected route/state and exact PNG path in a manifest, verify PNG dimensions from the files, and leave missing combinations open rather than submitting partial evidence as complete. If private values appear, mask only in the disposable browser DOM, record what was masked, and never persist the masking as a product change.
- Navigate directly to legacy routes and inspect the actual rendered hub/tab, menu, launcher, and dock state. For scrollable tab rails, compare the selected tab's rectangle with the rail at phone width and exercise a route change. A correct DOM state behind a boot, error, or transition overlay is not a clean visual pass; wait and recapture the unobstructed surface.
