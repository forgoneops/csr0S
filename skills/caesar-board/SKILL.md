# Board (notes and workplans)

Plugin `board`. Shared quick notes and workplans. A card may have up to 200 ordered checklist steps; completed notes stay visible. A step is done only after its assignee submits proof and a different agent verifies it.

## Use the CLI
`bun tools/board.ts add "text" [--priority high|normal|low] [--remind "2026-11-10 09:00"] [--color yellow|pink|blue|green|orange] [--note path/in/vault.md]`
`bun tools/board.ts list [--open]`
`bun tools/board.ts step-add <cardId> "step title"`
`bun tools/board.ts step-assign <cardId> <stepId> <profile>`
`bun tools/board.ts step <cardId> <stepId> start|submit|verify|return|block [proof or note]`

For Caesar and the main agent, use the `caesar-board` MCP tools supplied to their authorized turns; the host keeps the Board-only bearer out of chat and tool output. Other agents need an explicitly issued token and may use the CLI. Never print, paste or store a bearer token. Your name on a card comes from the token, so you cannot sign as someone else; the card shows "added by <you>".

## Rules
- Write notes in plain, human language—not raw commands, logs or role jargon. For ongoing work, make the goal, current step, next step and blockers legible; keep IDs and technical details secondary for traceability. A note is one short line (max 500 characters), understandable without context. Before any note-bearing Board mutation, count the exact note text and keep it within 500 characters; omit repeated findings rather than letting the Board truncate the conclusion or follow-up IDs. A workplan step title is at most 240 characters; count the complete proposed title before calling the tool, including prefixes and proof text.
- `high` only for what cannot wait; the rest is `normal` or `low`. Before creating work, check open cards and their steps for overlapping scope, not just matching titles; reuse existing work or identify the overlap rather than duplicate it.
- `--remind` only when he asked for a reminder or a deadline is real; it must be in the future, local time. One reminder per card goes out as a notification that opens the Board.
- `--note` is a path inside the vault (e.g. `Projects/Example.md`), never an absolute path.
- Before assigning a step to a profile, verify it appears in the live Lair crew roster and is ready; `hermes profile list` proves only that a Hermes profile exists. If the requested profile already exists but is absent from the roster, use Lair Hire with its exact profile slug as the name so it reuses that profile, then set the display name through Manage/Rename and verify the roster. Never hand-edit `crew.json` or create a duplicate profile just to get the desired display name.
- Only the card author or owner may add/edit its steps and assign them; the main agent may maintain workplan cards but cannot edit quick notes. Preserve requested step text exactly, including capitalization and punctuation; if the user refers to exact text given earlier, retrieve that source or the card's review history rather than reconstructing it. Validate the full step title against the limit before mutation; after a validation error, shorten the payload and retry only once. After adding, confirm success from the returned live card and capture the generated step ID; do not claim completion from an attempted call alone. Count the complete proposed step title programmatically or manually before mutation and keep it below the 240-character limit; validation rejects count toward the Board's repeated-reject circuit pause. After three rejected Board mutations in a turn, stop all Board mutation calls (including a different action such as return), do not route around the pause, and report which action did not complete. An assignee must start and submit their own step with an observable proof reference (URL, run/session ID, commit SHA, file/log path or screenshot path); the server rejects owner-initiated start attempts and plain completion claims such as `done`. If the operator explicitly directs the assignee to resume a blocked step, start it first, then submit only after confirming the live state is active; a blocked step cannot accept submission. Never temporarily reassign a step to bypass this actor check; if the assignee cannot act, leave the status open and report the blocker. For approval-gated work, treat an explicit operator-provided approval and date as evidence of the human decision, and independently check locally observable file, backup, and commit claims before including them in proof. Prefix extensionless relative paths with `./`; prefix all-letter short SHAs with `commit`; use an explicit label such as `run id: 2026` for numeric-only run IDs. A different agent reviews the reference before verification.
- Review in this order: read the live card and ordered steps; inspect the named acceptance source and each evidence artifact; independently rerun the relevant checks; map each acceptance criterion to observed evidence; then inspect follow-ups for every uncovered material criterion. A submitter's proof text, test summary, or claimed browser measurement is a lead, not evidence; rerun the named command and report the fresh counts exactly, since test suites and their totals can change between submissions. For Brain/vault deliverables, search the Brain first, then read each exact submitted path and confirm the count, author/ownership, required tag, substance, and absence of apparent secrets; local repository filename searches do not verify or disprove Brain artifacts, and code tests are irrelevant unless the step asks for them. Compare captures against the required live state, viewport, theme, mode, and language. Do not let passing tests/builds stand in for visual or interaction criteria, or let a submitter's coverage summary substitute for checking its artifact. For a complete submission, `verify` only when every required criterion is evidenced; otherwise `return` with exact unmet criteria and missing proof. For an explicitly PARTIAL submission, verify only a substantive, independently observed slice when every material gap has a directly scoped open follow-up; state the limited scope in the review note and make clear overall acceptance remains open. Treat a stated-vs-measured count or definition mismatch as a material gap, even when the submitted inventory faithfully applies its declared filter; do not reject accurate measurements, but create a narrowly scoped reconciliation follow-up when you have card-maintenance authority. Likewise, when a required test command runs and fails, preserve its fresh observed result and create a specific remediation follow-up rather than treating execution itself as a pass. If no suitable follow-up exists and you have authority, add and assign one to the responsible ready owner, then confirm it from a fresh full-card read; only return when you lack authority or the submitted slice is false/off-topic. Never let Board status `verified` imply that a partial step is fully accepted, and never verify your own submission. A workplan becomes done only when every step is verified; the owner can directly finish a simple note.
- When executing an assigned step, inspect recent history and named artifacts first, but treat prior submissions, status snapshots, and claimed checks as leads rather than current proof: confirm the named commit exists in this checkout, inspect the relevant files, and rerun checks needed for the present acceptance before reusing that evidence. For a review step dependent on an earlier deliverable, inspect that predecessor's live status and exact proof/report artifact before drawing conclusions. When a named report exists, read it and carry its actual findings, counts, limitations, and explicit unassessed areas into the review; do not replace report review with a status snapshot or claim that no report exists because an older submission says so. Distinguish the report's observed zero proposals from the stronger unsupported claim that no candidates exist. If the predecessor is blocked or has no submitted artifact, state that there are no proposals available to review and identify the precise prerequisite gap; do not present a local filename search or a missing Board attachment as proof that no proposals exist elsewhere. Submit only the evidenced review slice, labeled PARTIAL when the requested review cannot be completed, and preserve the distinction between “nothing was submitted” and “nothing exists.” Board reads may include historical or duplicate card snapshots; immediately before submit/block, read the live card and confirm the step is still active, then use the matching action. If a Board read is archived to a spillover file because its output is too large, inspect that saved artifact instead of repeating the oversized request; use a bounded query such as `jq -c '.cards[] | select(.id=="<cardId>") | {text,steps}' <spillover-file>` and validate the target card and ordered step IDs before relying on it. If the wrapper adds a line-number prefix, strip that prefix before parsing. Do not treat the truncated preview as the full card or claim the card is unreadable until the saved artifact has been checked. A provisional artifact or explicitly open coverage is the work to continue, not a reason to block. For visual/browser audits, inventory the requested routes and state dimensions, then use available browser automation to gather reproducible captures and update the matrix; distinguish source-inferred coverage from rendered evidence. For every material gap in a PARTIAL submission, inspect the full live card's ordered steps for an existing follow-up that directly implements or resolves it; do not rely on the submitter's claim that none exists, because later steps may already cover the gap. If none is suitable and you have authority to maintain the card, add a narrowly scoped implementation follow-up, assign it to the responsible ready crew member, then read back and confirm its scope, owner and open status before citing it. Adding a follow-up does not create a substantive slice to verify when no part of the submitted work is evidenced; return that submission and keep the new implementation work open. Treat adding, assigning, and verifying as dependent calls: capture the new step ID from the add result, assign that exact ID, then read back the card to confirm its exact scope, assignee, and open status before citing it in the verification note. A successful assignment response alone is not enough if its returned card was truncated; inspect the returned/live state. Keep state-changing Board actions and their confirmation reads sequential, not parallel: a concurrent read can return the pre-mutation snapshot, so wait for the action response and then read the target card/step to confirm the resulting status and note. Adding a follow-up does not make the uncovered criterion complete. Adding a follow-up does not make the uncovered criterion complete. Match the follow-up's stated deliverable to the gap: a broad final regression/sign-off step, a visual/theme step, or a downstream QA/review step does not implement missing route/state coverage or captures. Separate interaction requirements such as keyboard or touch behavior also need explicit coverage. If any material gap lacks a suitable follow-up, return the submission and identify the missing follow-up scope. Before deciding that proof is committed, use Git to verify every claimed artifact path is tracked by the named scoped commit; files merely present as untracked working-tree artifacts do not satisfy a commit requirement. For image evidence, open the actual capture and confirm its rendered route/state and dimensions; if available, inspect each required viewport, not just one representative screenshot. For a deep-link criterion, navigate directly to each required URL and confirm a stable route-specific heading or control after the app hydrates; an HTTP response, shell breadcrumb, generic loading text, or prior in-app navigation does not prove the target route rendered. Record each path's result separately and leave untested routes explicitly open. Do not submit partial evidence as complete. Before verifying a PARTIAL submission, inspect the full live card's ordered steps and confirm every material gap has an open follow-up whose deliverable directly implements or resolves that gap. A broad regression/sign-off or QA step can verify coverage but does not implement missing behavior, grant semantics, or route/state coverage. If none exists and you have authority to maintain the card, add and assign a narrowly scoped implementation follow-up, then read back its scope, owner, and open status; if you lack that authority, return the submission naming the exact missing follow-up scope. Adding a follow-up does not make the uncovered criterion complete or create a substantive slice to verify when none is evidenced. If a gate is visible, identify and activate its actual accessible control (for example, locate the button by its visible/accessible name and click that element) rather than guessing coordinates; wait for the transition and inspect a fresh capture before deciding the session is blocked. If acceptance requires an authenticated/live session and the gate remains after the documented interaction path, do not bypass credentials or authorization: record the exact visible gate, partial artifact, and remaining coverage, then block only on access to that session. A reachable URL or a screenshot of a boot/loading gate proves browser access, not usable application state. Never label partial evidence as meeting the full acceptance criteria. When the operator explicitly asks to submit existing partial proof for reviewer judgment, submit it with a clear coverage statement and exact gaps; keep the step open to review rather than disguising it as completion. If a requested heuristic check (such as Jev) recommends changes, record its result accurately. When the task explicitly gates a local commit on that check, do not commit after `fix` or `unverified`; resolve the finding or omit the commit. If the user explicitly requires partial submission, submit a clearly labeled PARTIAL proof with exact completed evidence and gaps where the Board still permits submission; the reviewer decides sufficiency. For explicitly submitted PARTIAL proof, verify only a substantive, independently evidenced slice that is genuinely part of the step; passing tests or a report alone do not establish a UI/interaction slice. For an implementation step, a design/acceptance contract or implementation plan is not an implementation slice, even when it accurately covers the requested behaviours; return it with the missing implementation criteria rather than verifying it as partial. When verifying a genuine partial slice, make the reviewer note explicit that Board status `verified` confirms only that slice, not full acceptance; name the uncovered criteria and the open follow-up, then report the outcome as “partial slice verified; overall acceptance remains open” so readers do not mistake workflow state for completion. A follow-up step may preserve the implementation work, but does not change what the submitted step itself evidences. Verify that every material gap has an open, named follow-up whose deliverable directly implements or resolves that gap; cite its exact ID and scope in the review note. A downstream QA/review step is not an implementation follow-up, and an existing partial artifact does not satisfy a gap merely because its dimensions or route match. If a gap has no suitable follow-up, return the submission and identify the missing follow-up step to add. A blocked step cannot accept a submission: after starting, read the live Board state before submitting, and if it is no longer active, do not retry submission as though it succeeded; report the status transition as the blocker.
- Check the live dispatcher before assigning: assigned open steps may start automatically even though adding a note alone does not start work. Add the complete ordered plan, safety boundaries and proof criteria before assigning; read back each card and count assignees after assignment.
- Distinguish human-gated work from preparation: a `#owner` tag may cause the dispatcher to skip the entire step, including preparation. If preparation must run automatically, put it in a separately assigned safe step and keep the gated application separate. Never treat a dependency written in step text as enforced scheduling; use an actual supported gate or explicitly report the risk.
- Send orders is a separate owner action and sends only selected notes to Caesar for routing. The main agent coordinates milestones and status but does not route or assign crew work.
- Agents cannot delete Board cards; only the owner can delete them until a card-specific, explicit deletion grant exists. Agents cannot reorder.

- After any Board mutation, make a fresh `board_list` read before claiming the resulting status, assignment, or verification. Mutation responses can contain a stale card snapshot even when the action succeeds; if the fresh read disagrees, report the observed state and do not claim success.

## API (same rules)
`GET /api/p/board/cards?done=0|1`, `POST /cards`, `PUT /cards/:id`, `POST /cards/:id/done {done}`, `DELETE /cards/:id` and `POST /cards/reorder {ids}` (owner only), all with `Authorization: Bearer <token>`. Errors come as `{ error }` (400 bad input, 401 no identity, 403 not allowed, 404 no such card).
